# Architecture and runtime contracts
React app (web/src) and Flutter app (mobile/lib) use shared JSON contract. Each record table carries school_id, UUID identity, same-school composite foreign keys and explicit RLS. Tenant data stays in one Supabase Postgres project. Auth login persists using the client SDK. Web grouping is local UI only; the DB is the authority. Both clients currently refresh manually after remote edits. Do not claim realtime or offline sync.

The four migrations in order: 001 foundation, 002 operational registers, 003 verified student/parent read scopes, 004 fee balance invoker view. DDL is additive; existing starter foundation untouched. Admin/staff permissions are currently school-wide; branch restriction and teacher-assigned class operations remain required before real data. Nine initial role names are supported by membership schema; no public role assignment. School admin is not a platform superuser. Verified links are operator-provisioned. Parent read access: own linked children, enrollment, associated class, attendance, homework and fees. Enrollments do not yet expire by academic term; avoid real student data until historical scopes are hardened.

Finance: actual invoice and payment RPC; duplicate payment request is checked; balance view uses RLS. Draft income, expense and salary records are not journal postings and are editable. No payroll, reconciliation, refunds, tax compliance or accounting ledger yet.

Native app wrappers are generated by the installed Flutter version to avoid stale Gradle/Xcode scaffolding. This ZIP excludes dependency caches and secrets.
